# Технічний аудит Gym Tracker

**Дата:** 24 жовтня 2026 року. **Обсяг:** поточний репозиторій `E:\Code\Gym`, версія застосунку 3.6.1. **Метод:** аналіз коду й конфігурації, локальні перевірки та актуальні advisory. Production-сайт і дані користувачів не змінювалися.

## 1. Executive Summary

Gym Tracker — невеликий статичний offline-first PWA для обліку тренувань і ваги. Svelte 5, TypeScript, Vite та GitHub Pages відповідають його масштабу; сервер і зовнішня БД не потрібні. Основний ризик пов'язаний із надійністю **єдиного локального сховища користувацьких даних**, особливо імпорту й міграції.

**Оцінка: 69/100; стан потребує запланованих покращень. Загальний ризик: високий для цілісності особистих даних. Упевненість: середня.** Це оцінка репозиторію, а не сертифікація безпеки чи перевірка production. **Знахідки: P0 — 0, P1 — 4, P2 — 5, P3 — 1.**

Найважливіше: (1) імпорт може частково переписати сховище; (2) стара міграція видаляє джерело при невдалому записі; (3) імпорт може мовчки відкинути записи пошкодженого бекапу; (4) зафіксована транзитивна high-уразливість `undici` зупиняє наявний CI-гейт. Заміна Svelte, Vite чи `localStorage` на серверну БД не обґрунтована. Перший крок — захистити відновлення/міграцію даних, додати сценарії збоїв до тестів, потім безпечно оновити транзитивні пакети й повторити локальні перевірки.

CSR достатній: застосунок приватного користування, сторінка не містить індексованого каталогу даних; SSR/SSG не дають практичної переваги. `robots.txt` і `sitemap.xml` описують тільки вхідну сторінку.

## 4. Детальні знахідки

### Цілісність даних

**ID:** DATA-01. **Категорія:** БД/цілісність. **Пріоритет:** P1. **Поточний стан:** імпорт послідовно викликає `saveAllProgress`, `saveWeights`, `saveExWeightHistory`, потім оновлює стан UI. **Проблема:** якщо другий або третій `localStorage.setItem` відмовить (квота/доступ), `persist()` відкочує тільки змінні Svelte; вже записані ключі залишаються новими. Перезавантаження змішає старі та імпортовані дані. **Докази:** `src/App.svelte:224–256`, `:86–105`; `src/lib/storage.ts:337–345`. **Рекомендація:** зберігати цілісний versioned snapshot одним ключем або зробити staging + commit/rollback усіх ключів; при помилці перевірити фактичний стан сховища й не показувати успіх. **Заміна:** три незалежні записи → один атомарний snapshot (після сумісної міграції). **Обґрунтування/результат:** `setItem` одного ключа усуває частковий імпорт; попередня копія потрібна на випадок помилки квоти. **Ризики:** зміна формату й сумісність старих даних; спочатку протестувати читання обох форматів. **Складність:** середня. **Залежності:** DATA-03 і тест аварійного імпорту. **Критерії готовності:** ін'єкція відмови на кожному кроці імпорту; після перезавантаження весь стан або старий, або новий. **Упевненість:** висока.

**ID:** DATA-02. **Категорія:** БД/міграція. **Пріоритет:** P1. **Поточний стан:** `loadAllProgress()` переносить старий ключ у v2 і в `finally` завжди викликає `safeRemoveItem(LEGACY_KEY)`. **Проблема:** при невдалому записі нового ключа старе джерело видаляється, а функція повертає `{}`. **Докази:** `src/lib/storage.ts:157–201`, особливо `:192–200`; тест успішної міграції є в `tests/storage.test.ts`, тест збою відсутній. **Рекомендація:** видаляти старий ключ тільки після успішного запису та read-back нового значення; у разі збою повертати валідований старий стан і показувати помилку. **Заміна:** немає. **Обґрунтування/результат:** відмова сховища не перетворюється на втрату прогресу. **Ризики:** повторна міграція за кожного запуску, доки запис не стане можливим; вона має бути ідемпотентною. **Складність:** мала. **Залежності:** тест із симуляцією `QuotaExceededError`. **Критерії готовності:** при відмові запису старий ключ зберігається й дані читаються повторно; при успіху міграція завершується один раз. **Упевненість:** висока.

**ID:** DATA-03. **Категорія:** БД/backup. **Пріоритет:** P1. **Поточний стан:** парсери на імпорті видаляють невалідні дні, вправи й записи ваги, але повертають `ok: true`, якщо верхні секції мають правильні типи. **Проблема:** частково пошкоджений або несумісний бекап може замінити всі поточні дані неповним набором без повідомлення, скільки відкинуто. Поточний тест саме очікує таку поведінку. **Докази:** `src/lib/backup.ts:65–97`, `src/lib/storage.ts:140–156`, `:208–215`, `:274–292`, `tests/backup.test.ts` (`sanitizes entries on import`), `src/App.svelte:241–255`. **Рекомендація:** для відновлення застосовувати строгий парсер або показувати точний звіт втрат і вимагати окремого підтвердження перед заміною; зберегти можливість «витягти валідне» як явний recovery-режим. **Заміна:** мовчазна санація імпорту → явний звіт/строгий імпорт. **Обґрунтування/результат:** користувач не втратить записи через тихе очищення. **Ризики:** старі бекапи можуть мати відхилення; підтримати v1/v2 і перевірити fixtures. **Складність:** середня. **Залежності:** DATA-01 перед фінальним застосуванням імпорту. **Критерії готовності:** змішаний валідний/невалідний файл не замінює дані без явного попередження; кількість відкинутих записів відома. **Упевненість:** висока.

**ID:** DATA-04. **Категорія:** БД/надійність. **Пріоритет:** P2. **Поточний стан:** особисті дані існують лише в `localStorage`; експорт запускається вручну, перевірки відновлення бекапу для користувача немає. **Проблема:** очищення site data, зміна пристрою/браузера або недоступність сховища можуть позбавити користувача єдиної копії. Це властивість архітектури, а не зафіксований інцидент. **Докази:** `README.md` (Features, Backup), `src/lib/storage.ts:18–26`, `src/App.svelte:201–257`. **Рекомендація:** додати видиму інструкцію регулярного експорту, дату останнього бекапу та перевірку round-trip файлу перед підтвердженням; за потреби нагадування про експорт. **Заміна:** немає; серверну БД не вводити без вимоги синхронізації. **Обґрунтування/результат:** просте відновлення без серверних витрат і збереження offline-моделі. **Ризики:** файл бекапу містить персональні дані; пояснити безпечне зберігання. **Складність:** мала/середня. **Залежності:** DATA-01/03. **Критерії готовності:** документований і протестований цикл експорт → імпорт у порожній профіль із порівнянням записів. **Упевненість:** висока щодо відсутності автоматичного резервування; фактичну поведінку браузерів користувачів не перевірено.

**ID:** DATA-05. **Категорія:** БД/модель. **Пріоритет:** P2. **Поточний стан:** завантаження обрізає прогрес до 3700 днів, вагу тіла до 5000 записів і історію кожної вправи до 500 точок. **Проблема:** після наступного збереження відкинуті старі записи зникнуть остаточно; межа 500 тренувань для однієї вправи може досягатися раніше за 10 років. **Докази:** `src/lib/storage.ts:24–26`, `:108–116`, `:208–215`, `:274–292`; `src/App.svelte:37–40`, `:287–292`. **Рекомендація:** встановити політику збереження даних, попереджати до обрізання/архівувати повну історію в експорті або обґрунтувати межі вимірами квоти. **Заміна:** немає. **Обґрунтування/результат:** давня історія не зникає без відома користувача. **Ризики:** більший обсяг `localStorage`; виміряти типовий і граничний JSON. **Складність:** середня. **Залежності:** DATA-04. **Критерії готовності:** тест на межі кожного ліміту і задокументована політика втрат/архіву. **Упевненість:** висока щодо обрізання, середня щодо ймовірності досягнення межі.

### Безпека і залежності

**ID:** DEP-01. **Категорія:** технології/безпека. **Пріоритет:** P1 через блокування CI, не через доведену експлуатацію production. **Поточний стан:** lockfile встановлює `undici@8.11.2` через `jsdom`, `fast-uri@3.1.8` і `serialize-javascript@7.0.7` через `vite-plugin-pwa`/Workbox. **Проблема:** `npm audit --json` 24.10.2026 повернув 1 high, 1 moderate, 1 low; `.github/workflows/ci.yml` і локальний реліз виконують `npm audit --audit-level=high`, тож на цих залежностях гейт завершується помилкою. Усі три пакети dev/build-path; шлях експлуатації в зібраному PWA не підтверджено. **Докази:** `package-lock.json`, `npm ls undici fast-uri serialize-javascript --all`, `.github/workflows/ci.yml`, `scripts/Release-Local.ps1`; advisory [undici GHSA-xjj6-f33q-929c](https://github.com/advisories/GHSA-xjj6-f33q-929c) (виправлено в 8.12.2), [fast-uri GHSA-w74x-v6f9-j3xg](https://github.com/advisories/GHSA-w74x-v6f9-j3xg) (3.1.9), [serialize-javascript GHSA-m5mm-p8h7-m29v](https://github.com/advisories/GHSA-m5mm-p8h7-m29v) (7.1.3). **Рекомендація:** оновити сумісні транзитивні версії через lockfile/батьківські пакети, потім повторити аудит, тести, збірку й offline-PWA перевірку; не вимикати audit-гейт. **Заміна:** `undici 8.11.2 → >=8.12.2`, `fast-uri 3.1.8 → >=3.1.9`, `serialize-javascript 7.0.7 → >=7.1.3` у сумісних major-лініях. **Обґрунтування/результат:** закриває відомі advisory без переписування стеку. **Ризики:** оновлення Workbox/PWA може змінити precache; перевірити офлайн-запуск після чистої інсталяції. **Складність:** мала/середня. **Залежності:** окрема гілка оновлення lockfile. **Критерії готовності:** `npm audit --audit-level=high` проходить, відомі три GHSA відсутні, E2E/offline smoke пройдено. **Упевненість:** висока щодо версій і гейта, низька щодо реальної експлуатованості в цьому проєкті.

**ID:** LOGIC-01. **Категорія:** архітектура/дані. **Пріоритет:** P2. **Поточний стан:** якщо для вибраної дати немає точної ваги вправи, `resolveExWeight()` бере останній запис усієї історії, навіть якщо той зроблено пізніше вибраного дня. **Проблема:** історичний екран показує майбутнє значення як «останнє», а діалог редагування отримує його як початкове. **Докази:** `src/lib/exweights.ts:29–50`, `src/App.svelte:295–298`. **Рекомендація:** для історичної дати шукати останній запис `<= date`, а якщо його немає — не показувати вагу; додати тест навігації в минуле. **Заміна:** немає. **Обґрунтування/результат:** підказка відповідає стану на вибраний день. **Ризики:** зміна звичного показу ваги при перегляді минулих днів. **Складність:** мала. **Залежності:** немає. **Критерії готовності:** тест із точками до й після вибраної дати показує тільки попередню. **Упевненість:** висока.

## 5. Аудит БД і даних

**Висновок: залишити браузерне сховище, оптимізувати цілісність і backup; міграція до серверної/SQL/документної БД зараз не виправдана.** Дані невеликі, належать одному користувачу на одному браузерному профілі, мережевої синхронізації або багатокористувацьких запитів немає. Вартість сервера, облікових записів, авторизації й захисту персональних даних перевищила б доведену користь.

Модель: дата `YYYY-MM-DD` → кількість підходів за ключем вправи; масив вимірювань ваги `{id,date,weight}`; історія ваги вправи за ключем із точками `{date,weight}`. `storage.ts` валідує календарні дати, діапазон чисел, відомі ключі, нормалізує v1/v2 та дедуплікує точки ваг вправ. `App.svelte:343–390` забезпечує одну вагу тіла на дату при редагуванні через UI, але `parseWeights()` не дедуплікує імпортовані записи за `id`/датою — інваріант не забезпечено на межі імпорту. Для невеликої кількості даних індекси, connection pooling, SQL-плани й транзакції СУБД не застосовуються; локальні масиви сортуються в пам'яті. Найважливіший аналог транзакції — безпечна заміна всіх ключів під час імпорту (DATA-01). Питання часових зон зменшує зберігання локальних календарних дат без часу; `exportedAt` містить UTC ISO-час. Грошових значень немає.

Конфлікти між вкладками потенційні: `storage`-подія в `src/App.svelte:427–434` перезавантажує стан після чужого запису, але операції типу read-modify-write не блокуються; при одночасному редагуванні діє «останній запис перемагає». Це гіпотеза про рідкісний режим, для пріоритезації потрібен сценарій двох вкладок і реальна потреба паралельної роботи. Квоти/обсяги, фактичний RPO/RTO та відновлення після очищення browser data не вимірювалися. Доступ до даних визначає браузерний origin; серверних прав доступу, tenant-ізоляції й production-БД немає. Дані `localStorage` не слід вважати зашифрованими на спільному пристрої.

## 7. Що залишити без змін

- Статичну клієнтську архітектуру з Svelte/TypeScript/Vite: невеликий застосунок, жодних серверних інтеграцій; `npm run check`, lint і тести проходять.
- `localStorage` як базове персональне сховище за умови виправлення запису/відновлення; SQL-індекси й окремий сервер не потрібні.
- Явний allowlist ключів вправ, перевірку дат/діапазонів, versioned backup і старі міграції після усунення DATA-02/03.
- PWA з precache й коректним `base` для GitHub Pages; абсолютний `navigateFallback` відповідає чинному шляху в конфігурації. Фактичний offline reload ще треба перевірити.
- Локальний процес релізу як основний. Ручний GitHub Actions fallback існує в репозиторії, але не потрібен для поточного аудиту чи виконання рекомендацій.
- CSP у `index.html`, відсутність `{@html}`/`innerHTML` у `src/` і відсутність сторонніх мережевих викликів у runtime; окремий pentest не виконувався.

## 8. Що можна спростити або прибрати

- Після підтвердженої міграції всіх профілів прибрати дубльовані функції старого формату ваг вправ (`loadExWeights`/`saveExWeights`) тільки разом із планом сумісності; зараз старий ключ потрібен для переходу й rollback.
- Замінити формальні offline/quota тести реальними сценаріями замість нарощування їх кількості. Це зменшить хибне відчуття покриття.
- Зробити `MIGRATION_PLAN.md` історичним документом і залишити актуальний релізний runbook в одному місці. Не видаляти історію міграції без потреби.
- Не додавати окремі cache/queue/analytics-сервіси: поточні розрахунки локальні. Профілювання потрібне лише якщо з'являться скарги або виміряна затримка.

## 9. Цільова архітектура

Один CSR/PWA з тим самим Svelte UI; чисті функції для тренувань і розрахунків; невеликий шар зберігання, що читає старі ключі, валідовує весь snapshot, записує його атомарно і повідомляє про помилки. Versioned JSON-експорт з попередньою перевіркою та явним звітом втрат. Static assets з GitHub Pages та service worker; локальні перевірки перед публікацією; зафіксований commit збірки та процедура відкату. Для спостереження достатньо локальних сигналів помилок сховища, ручного offline smoke та періодичного Lighthouse; віддалена телеметрія з персональними даними не потрібна без вимоги продукту.
